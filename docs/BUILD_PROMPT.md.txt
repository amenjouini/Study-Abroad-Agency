## 4. Product

A CRM and student portal for a Tunisia-based agency that helps Tunisian students study in Italy.

- **OWNER / ADMIN** — manages the whole agency.
- **STAFF** — manages assigned students within the permissions granted to them.
- **STUDENT** — personal portal to follow their Italy-study journey, upload documents, see payments and requirements, book agency appointments and message the agency.

Architect for other destinations later (Tunisia → France, Germany, Canada, Spain, Turkey): Country → Procedure → Academic year → Version → Requirements → Rules → Deadlines. Do not hard-code "Italy" into the table design.

## 5. Roles and permissions

**ADMIN / OWNER:** everything — staff, students, leads, applications, documents, document rules, procedures, universities, scholarships, payments, appointments, settings, analytics, audit logs.

**STAFF:** permissions granted per area (students, documents, payments, applications, appointments, scholarships, visa). Access is limited to assigned cases unless a permission grants wider access. Staff cannot change the owner account, critical settings or document rules without an explicit permission.

**STUDENT:** only their own data. Can register and log in, complete their profile, choose language and study preferences, manage their applications, upload and replace documents, see document and payment status, book agency appointments, message assigned staff, track visa, Universitaly and scholarship, see deadlines and progress. Never sees internal notes, internal comments, other students or agency financial data.

Implement permissions as data (role → permissions, plus per-user grants), checked through one server-side helper, for example:

```ts
await requirePermission(user, "documents.review", { caseId });
```

## 6. Student journey

```
LEAD → REGISTRATION → PERSONAL PROFILE → LANGUAGE → ACADEMIC PROFILE
→ CITY / UNIVERSITY / PROGRAM → UNIVERSITY APPLICATION → ADMISSION
→ UNIVERSITALY → SCHOLARSHIP → FINANCIAL DOCUMENTATION → VISA DOCUMENTATION
→ VISA APPOINTMENT → VISA SUBMISSION → VISA DECISION → TRAVEL
→ ARRIVAL IN ITALY → PERMESSO DI SOGGIORNO → FINAL ENROLLMENT
```

This is not a rigid linear process. Stages are configurable data. Students can apply to several universities, be rejected by one, change university, have several funding sources, have documents rejected, need human intervention, and run into scholarship or visa problems. Every stage change is recorded in `case_stage_history` and appears on the case timeline.

## 8. Money

- Store amounts as integer minor units plus ISO 4217 currency code. **TND has 3 decimals (millimes); EUR has 2.** Formatting and parsing must use the currency's own number of decimals.
- Never add amounts in different currencies.
- Agency fees and payment plans are normally in TND. Procedure financial requirements are in EUR.
- A TND funding source counts toward a EUR requirement only through a staff-entered EUR value, with the exchange rate, the rate date and the staff member recorded on the funding source. No automatic conversion.

## 9. The core feature: dynamic document requirement engine

The heart of this application is not the dashboard. It is the engine that determines which documents a student needs from their actual situation.

Example input: nationality Tunisian, destination Italy, academic year 2026/27, sponsor Father, sponsor status Employee → personalized checklist. Change the sponsor to Retired or Business owner and the checklist changes. Unsupported or ambiguous relationship → `REQUIRES_HUMAN_REVIEW`.

Do not build a static checklist.

### 9.1 Engine design

- Implement the engine as a pure module in `lib/engine/`.
  - **Input:** a "case facts" object (student, sponsors, funding sources, university application, program, academic year, scholarship, visa, existing documents) plus the case's procedure version.
  - **Output:** the required requirement instances, calculated values (funding shortfall, passport check, deadlines) and human-review flags with reasons.
- The engine does not read the database. A separate service loads the facts, calls the engine and persists the result.
- Deterministic: same input, same output. This is what the tests exercise.

### 9.2 Rules

Rules are condition trees with the groups `AND`, `OR`, `NOT`.

Operators (use exactly these names):

```
equals, not_equals, in, not_in, gt, gte, lt, lte, between, before, after, exists, not_exists
```

Value types: string, enum, number, currency (amount + currency), date, boolean, calculated value.

Rules can reference: student, sponsor, funding source, university, program, academic year, scholarship, application, visa, documents.

Example:

```
IF sponsor.relationship IN [FATHER, MOTHER, SIBLING, GRANDPARENT, UNCLE_AUNT, COUSIN]
AND sponsor.professional_status = EMPLOYEE
THEN require for that sponsor:
  EMPLOYMENT_CERTIFICATE, PAYSLIPS_LAST_6, CNSS_CERTIFICATE, BANK_STATEMENT_6_MONTHS,
  SPONSOR_ID, RELATIONSHIP_PROOF
```

Admins create and edit rules from the dashboard (section 22).

### 9.3 Requirement instances

Never store documents as fields such as `student.bank_statement`. A requirement definition (e.g. `BANK_STATEMENT`) produces one instance per subject: "Father → Bank statement" and "Uncle → Bank statement" are separate instances.

Each instance has: case, requirement, subject (student, sponsor or funding source), status, deadline, documents, reviewer, rejection reason, history, and calculated results where applicable.

### 9.4 Re-evaluation

When facts change (for example the sponsor switches from Employee to Retired), re-run the engine:

- add newly required instances;
- mark instances that no longer apply as `NOT_APPLICABLE` — never delete them, and keep any uploaded documents and versions attached;
- record the change in the audit log and on the case timeline.

### 9.5 Dependencies

Requirements can depend on other requirements:

```
DIPLOMA → LEGALIZATION → TRANSLATION → APOSTILLE → DECLARATION_OF_VALUE
```

A dependent requirement cannot be completed until its prerequisites are satisfied. Pathways differ per student (secondary diploma vs university degree, Declaration of Value vs CIMEA); model them as data, not code.

### 9.6 Document formalities

Track separately per document version: uploaded, original presented, signed, stamped, translated, legalized, apostilled, approved. These are not the same thing.

Financial documents may need originals signed and stamped by the issuer. The bank blocking letter additionally needs the branch manager's signature and a RIB.

### 9.7 Statuses

```
NOT_STARTED, REQUESTED, UPLOADED, UNDER_REVIEW, APPROVED, REJECTED,
NEEDS_CORRECTION, EXPIRED, NOT_APPLICABLE, REQUIRES_HUMAN_REVIEW
```

### 9.8 Versioning

Never destroy previous versions. Passport v1 rejected, Passport v2 approved: staff see the complete history. Each version stores uploaded_by, upload date, file, status, reviewer, review date, rejection reason and comments.

## 10. Funding model

A student can have several funding sources. Do not assume one sponsor.

Example: Father €5,000 + Scholarship €4,000 + Other eligible source €1,179.85.

The engine calculates **Required, Available, Shortfall, Surplus** from the case's procedure version.

Example: Required €10,179.85 − Scholarship €6,000 − Eligible family funding €2,500 → Shortfall €1,679.85.

Family sponsors are limited by the procedure version. For 2026/27 (Embassy Tunis): relatives within the 4th degree — father, mother, brothers and sisters, grandparents, uncles and aunts, blood cousins. The relationship must be proven with original civil-status records, translated into Italian, legalized and apostilled.

- Relationship unclear or outside that list → `REQUIRES_HUMAN_REVIEW`.
- `SELF_FUNDED` is not listed in the 2026/27 Embassy text → `REQUIRES_HUMAN_REVIEW`.
- Institutional funding (Italian institutions including universities, local governments, foreign bodies the Embassy considers reliable) is a separate funding-source type, not a sponsor.

Scholarship rules for 2026/27:

- If a scholarship is below the published minimum, the shortfall must be covered by other eligible funding.
- An Italian government scholarship at or above the published minimum waives the bank blocking requirement. Do not apply this to every scholarship.
- For programs shorter than 12 months, the engine proposes a proportionally reduced amount, flagged for staff confirmation.

## 12. Seed data: "Italy — Study visa (university enrollment) — Tunisia", 2026/27, version 1, ACTIVE

### Visa appointment

- General deadline for fixing visa appointments: **30 November 2026**.
- Universities may set earlier per-program dates; the effective deadline is the earliest (section 14).
- ALMAVIVA contacts students by email, at the address entered in Universitaly, once the validated pre-enrolment has been transmitted to the Embassy. Store `universitaly_contact_email` and tell students clearly to monitor that inbox.
- ALMAVIVA appointment dates cannot be changed.
- Processing time: up to 90 days from dossier submission.
- Do not build any messaging suggesting the agency can obtain, buy or speed up appointments.

### Financial requirement

Store all published values. Do not derive one from another.

```
monthly_reference_amount = 783.06 EUR
months                   = 13
published_minimum_total  = 10179.85 EUR   (applicable minimum)
```

Note: 783.06 × 13 = 10,179.78. The Embassy publishes 10,179.85. Use the published total.

### Bank blocking ("déclaration de blocage")

Model: monthly amount, number of months, published minimum, blocked amount, blocking period (one year), irrevocable flag, bank and branch, branch-manager signature required, RIB required, and exceptions (e.g. a qualifying Italian government scholarship).

### Passport (calculated requirement, not a checkbox)

```
satisfied when: passport_expiry_date > reference_date + 15 months
reference_date = visa appointment date if known, otherwise planned submission date
```

Store `reference_date` and the result on the requirement instance; recompute when the appointment date changes. The 15-month value is a procedure parameter, not a constant.

### Other 2026/27 requirements (seed each with its source URL)

- Visa application form, completed and signed
- One recent passport photo (ICAO format)
- Universitaly pre-enrolment letter, validated and transmitted to the Embassy by the university
- Final secondary diploma: original + copy, translated into Italian, apostilled, with Declaration of Value or CIMEA certificate (diploma pathway configurable per degree level)
- Academic suitability certificate where applicable
- Language certificate: Italian-taught courses require Italian at B2 or above; English-taught courses require adequate proof of English; the Embassy may verify by interview
- Travel reservation (return) or proof of own means of travel
- Proof of accommodation, at least for the initial period
- Health insurance in one of three accepted forms (consular declaration under a bilateral agreement; foreign policy with consular declaration; Italian policy with insurer declaration)
- Proof of financial means (section 10) and bank blocking (above)
- Student's birth extract and family status: original, apostilled, translated into Italian
- Socio-economic situation document issued by the competent Tunisian ministry
- Optional short motivation letter

General: all documents in French, translated into Italian and apostilled. The Embassy may request additional documents or an interview.

### Diploma legalization (required since 30 March 2026, before the Declaration of Value)

- Secondary diplomas → Tunisian Ministry of Education
- University degrees → Ministry of Higher Education and Scientific Research / rectorates
- Vocational titles → Ministry of Employment and Vocational Training
- Health titles → Ministry of Health

### Deadlines and consistency checks

- **Enrollment on Universitaly by 31 January 2027.** The Embassy revokes visas of students not enrolled by then. Versioned deadline.
- **Course/visa consistency:** flag `visa_case.program ≠ intended enrollment program` as a serious issue → `REQUIRES_HUMAN_REVIEW`. Enrolling in a different course requires returning to Tunisia for a new visa. Never present this as a casual course change.
- **Permesso di soggiorno** — store both deadlines on the record, each with source and calculation method:
  - legal deadline: arrival date + 8 working days, Italian holidays excluded (`WORKING_DAYS`, basis art. 5 c.2 D.lgs. 286/1998);
  - conservative student-facing deadline: arrival date + 8 calendar days (`CALENDAR_DAYS`, source: Embassy notice).
  - Show the conservative date prominently to students, plus: "Students waiting for their first permesso should not leave Italy."

### 2027/28 version (for versioning demo)

Seed "2027/28, version 1, DRAFT" containing only the visa-appointment deadline of **31 October 2027** from the MUR circular. Do not copy 2026/27 financial values into it.

Prominent student button. The student describes the problem, can attach documents and request an agency appointment. The case gets `REQUIRES_HUMAN_REVIEW` with a priority (`NORMAL, HIGH, URGENT`). The staff dashboard shows these cases at the top.

### Payments

- Statuses: `PENDING, PARTIALLY_PAID, PAID, LATE, CANCELLED`

### Messaging and notifications

- Student ↔ assigned staff messaging with text, attachments and document references.
- Important actions create timeline entries: document uploaded, approved, rejected; payment recorded; appointment created; visa stage changed.

### Leads

### Knowledge base

Articles with title, content, language, category, academic year, source, official URL, last verified, published flag.

## 20. Security

The application handles passports, identity documents, family records, financial records and visa information.

- Secure authentication; server-side authorization on every data access; RBAC with granular permissions
- Private storage; short-lived signed URLs or an authorized download route; no public document URLs
- Upload validation: MIME sniffing plus extension check, size limit (10 MB default, configurable)
- Rate limiting on authentication and uploads
- Zod validation on every input; CSRF protection where applicable; XSS-safe rendering
- Secure HTTP-only cookies; secrets only in environment variables
- Consent recorded at registration (timestamp, policy version)
- Configurable document retention; no permanent deletion without an admin workflow
- Architecture allows configuring database and file backups

## 26. Tests (Vitest)

Test business logic, not just UI.

**Engine**
- Employee sponsor → correct instances
- Retired sponsor → correct instances
- Business-owner sponsor → correct instances
- Unsupported relationship → `REQUIRES_HUMAN_REVIEW`
- Self-funded → `REQUIRES_HUMAN_REVIEW`
- Two sponsors → separate requirement instances
- Re-evaluation marks dropped instances `NOT_APPLICABLE` and keeps their documents
- A dependent requirement cannot complete before its prerequisite

**Funding**
- 10,179.85 − 6,000 − 2,500 = shortfall 1,679.85
- Published minimum is read from the procedure version (assert 10,179.85, not 10,179.78)
- Adding amounts in different currencies is rejected
- TND formats and parses with 3 decimals

**Passport**
- Pass and fail around the 15-month boundary
- Result recomputed when the appointment date changes

**Deadlines**
- Effective deadline = earliest of the available values
- Working days skip weekends and Italian holidays
- Permesso: legal and conservative deadlines both calculated

**Applications**
- Several applications per student
- Visa and Universitaly attached to the correct application
- Course/visa mismatch flagged

**Permissions**
- A student cannot read another student's documents
- staff2 cannot access staff@'s cases
- Admin can access everything

**Versioning**
- Old document versions remain accessible after replacement
