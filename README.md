# bon-ita — Study-in-Italy agency CRM & student portal

A CRM and student portal for a Tunisia-based agency that helps Tunisian students study in Italy. The core of the app is a
**dynamic document-requirement engine**: the checklist each student sees is computed from their real situation
(sponsor relationship and status, funding, program language, scholarship, visa, …) and the active procedure version —
never a static list. Rules, amounts, deadlines and thresholds are data stored under a procedure version and editable by admins.

Full specification: [docs/BUILD_PROMPT.md](docs/BUILD_PROMPT.md) · Progress and known gaps: [docs/PROGRESS.md](docs/PROGRESS.md).

## Requirements

- Node.js 22+ and npm
- PostgreSQL 16+ — via Docker (recommended) or your own server. **No other database is supported.**
- Optional: MinIO / any S3-compatible service for production file storage

## Setup

```bash
npm install
cp .env.example .env            # then set BETTER_AUTH_SECRET, DOWNLOAD_SIGNING_SECRET, CRON_SECRET
npm run db:up                   # PostgreSQL (5432) + MinIO (9000/9001) with docker compose
npm run db:migrate              # apply migrations
npm run db:seed                 # reference data, 2026/27 procedure, demo accounts and students
npm run dev                     # http://localhost:3000
```

**No Docker?** `npm run db:local` starts a real PostgreSQL server from the official binaries (npm package
`embedded-postgres`) on `localhost:5432` with the same credentials as `docker-compose.yml`; keep it running in one terminal,
then run the migrate / seed / dev commands above. Data lives in `./.pgdata` (git-ignored).

Other commands: `npm test` · `npm run typecheck` · `npm run lint` · `npm run build` · `npm run db:reset` (wipes the database and re-seeds — development only).

## Testing

`npm test` runs Vitest:

- pure unit tests (engine, money, dates, deadlines, passport rule, appointments, CSV, i18n catalogs, RTL);
- **integration tests against a throwaway database** (`<name>_test`): it is dropped, migrated and seeded before every run, so the dev
  database is never touched. If PostgreSQL is not reachable the DB tests are skipped with a warning; set `REQUIRE_DB_TESTS=1` to make that an error.

## Storage

`STORAGE_DRIVER=local` writes to `./storage` (git-ignored, never served statically). `STORAGE_DRIVER=s3` uses any S3-compatible
service (MinIO in `docker-compose.yml`; create the bucket named in `S3_BUCKET`). Files are only served through the authorized routes
`/api/documents/[versionId]`, `/api/attachments/[id]` and `/api/payments/receipt/[id]`.

## Scheduled reminders

Deadline, payment-due and appointment-tomorrow notifications are produced by `POST /api/cron/reminders` with header
`Authorization: Bearer $CRON_SECRET`. Call it once or twice a day from any scheduler. It is idempotent.

## Deploying to Render

[`render.yaml`](render.yaml) is a [Render Blueprint](https://render.com/docs/blueprint-spec): it provisions the web
service and a managed PostgreSQL database together.

1. Push this repository to GitHub or GitLab.
2. In the Render dashboard: **New → Blueprint**, pick the repo. Render reads `render.yaml`.
3. When prompted, fill in **`OWNER_EMAIL`** and **`OWNER_PASSWORD`** (at least 10 characters) — your first real
   login. Every other secret (`BETTER_AUTH_SECRET`, `DOWNLOAD_SIGNING_SECRET`, `CRON_SECRET`) is generated by Render.
4. Deploy. The blueprint's `preDeployCommand` applies migrations (`prisma migrate deploy`) and seeds reference
   data — countries, academic years, the 2026/27 procedure, DSU Toscana, Italian holidays — before each deploy;
   both are idempotent, so re-deploys are safe. `SEED_DEMO=false` is set explicitly: the five fictional demo
   students and their published dev passwords are never created in this deployment. Your `OWNER_EMAIL` /
   `OWNER_PASSWORD` account is created once, the same way.
5. Once the service is live, open **`BETTER_AUTH_URL`** and **`NEXT_PUBLIC_APP_URL`** in the service's Environment
   tab and check they match the actual `https://<service>.onrender.com` address (or your custom domain) shown at
   the top of the dashboard — Render may have appended a suffix if `bon-ita` was taken. If you change them, save
   to trigger a rebuild: `NEXT_PUBLIC_APP_URL` is inlined into the client bundle at build time, so it only takes
   effect after a rebuild, not a restart.
6. Sign in at `/login` with `OWNER_EMAIL` / `OWNER_PASSWORD`, then create real staff accounts from
   `/admin/staff` (passwords are shown once, exactly like the lead-conversion flow).
7. Point an external scheduler (e.g. [cron-job.org](https://cron-job.org), GitHub Actions, Render's own Cron
   Jobs) at `POST https://<service>.onrender.com/api/cron/reminders` with header
   `Authorization: Bearer <CRON_SECRET>` (copy the generated value from the Environment tab) once or twice a day.

Notes:

- **Storage** defaults to a [Render Disk](https://render.com/docs/disks) mounted at `/var/data`
  (`STORAGE_DRIVER=local`, `STORAGE_LOCAL_DIR=/var/data/storage`). A Disk attaches to a single instance, which
  fits the `starter` plan. To scale to multiple instances, switch `STORAGE_DRIVER` to `s3` and set the `S3_*`
  vars to an S3-compatible service (Cloudflare R2, Backblaze B2, or your own MinIO) instead of the disk.
- The `starter` web and database plans are the smallest paid tier; adjust `plan:` in `render.yaml` as needed.
- `GET /api/health` (no auth) is used as the health-check path; it only confirms the database is reachable.
- To upgrade the demo/reference seed data later (e.g. a new academic year), edit `prisma/seed/` and push —
  `preDeployCommand` re-runs the seed on every deploy.

## Layout

```
prisma/            schema, migrations, seed (procedure data: prisma/seed/procedure-data.ts)
src/lib/engine/    pure rule / funding / passport / deadline / dependency engine (unit-tested)
src/lib/           money, dates, permissions catalog, upload validation, CSV, formatting
src/server/        services: facts + procedure loading, engine persistence, documents, payments, admin, procedures …
src/app/           Next.js routes: /student, /staff, /admin, /api
messages/          next-intl catalogs per locale and feature (fr, en, ar, it)
tests/             Vitest suites (tests/db = integration)
```
